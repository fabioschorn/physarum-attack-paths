Changes since v1 evidence
--------------------------
  The Manager's review identified that the /candidate-discoveries API showed
  trigger=scheduled because the startup scan's HashMap insert overwrote the
  earlier eBPF-triggered entry.

  Fixes applied in commit 6b50ee7:
    1. DiscoveryTrigger::priority() added to physarum-protocol:
         EbpfNewOutboundHost | EbpfNewInboundHost => 2
         Scheduled                                => 1
         Startup                                  => 0

    2. Server candidate upsert changed from store.insert() to Entry API with
       priority check: only update if incoming trigger has strictly higher
       priority than the stored one. scheduled never overwrites
       ebpf_new_outbound_host.

    3. Agent ebpf_seed_loop: when dst_ip is already in discovered_sockets,
       skip the /32 scan but still POST an eBPF-triggered candidate report
       so the server can upgrade the trigger provenance (priority upsert).

    4. New log line: "eBPF seed scan: starting exact-host scan
       seed_cidr=<ip>/32" — explicit evidence of the /32 scope.

    5. Two new server-side tests added:
         ebpf_trigger_not_overwritten_by_later_scheduled_discovery
         ebpf_trigger_promotes_over_earlier_scheduled_entry

Manager blocker resolution
--------------------------
  Original blocker: "the API evidence no longer proves the candidate was
  eBPF-triggered" because HashMap::insert() let scheduled overwrite ebpf trigger.

  Resolution:
    - Server: DiscoveryTrigger::priority() + Entry API upsert — ebpf_new_outbound_host
      always wins regardless of arrival order (2 > 1). Two new tests verify both
      directions (eBPF first and scheduled first).
    - Agent: When dst_ip is already in discovered_sockets, ebpf_seed_loop still
      posts a trigger-provenance report (no rescan, just provenance assertion).
      This guarantees the API shows ebpf_new_outbound_host even when the
      startup scan won the race.
    - Evidence 4 now shows trigger=ebpf_new_outbound_host directly in the API
      response — no log workaround needed.
